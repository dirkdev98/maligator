# VM target and program images

## Context

Maligator has two execution backends over one optimized program: a bytecode
interpreter and generated native C. The old target boundary treated the lowered
program as one VM definition. Runtime semantics, native-only optimization choices,
GC policy, and diagnostics were mixed together, while emitters could rediscover
facts from bytecode. That made information ownership ambiguous and made it possible
for the interpreted and compiled paths to drift.

The target architecture must support ordinary mutable JavaScript and progressively
stronger whole-program facts. In particular, it must remain suitable for closed-world
reachability and primordial DCE, object-shape lowering, interprocedural representation
work, and GC-aware call ABIs without creating separate optimization pipelines.

## Decision

The compiler uses four explicit boundaries:

```text
SemanticProgram
    -> CoreCompilation { program: CoreProgram, context: CoreCompilationContext }
    -> ExecutionProgram
    -> ProgramImage { runtime: RuntimeImage, native: NativePlan, diagnostics }
    -> runtime wire, compiler artifact, interpreted execution, or native C
```

Each boundary owns a different kind of information:

| Boundary                 | Owned information                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CoreProgram`            | Canonical optimizing SSA: values, control flow, memory, effects, representations, and proof obligations.                                                                                          |
| `CoreCompilationContext` | Program facts and non-SSA inputs: world and closure policy, retained source data, module order, and host candidates.                                                                              |
| `ExecutionProgram`       | Verified executable semantics after allocation: physical registers, representations, parallel-copy schedules, exact per-safepoint liveness, and plan-lowered specialization decisions.            |
| `RuntimeImage`           | Backend-independent runtime data: bytecode functions, constants, globals, exception/debug tables, literal shapes, CommonJS entries, and the host-install manifest.                                |
| `NativePlan`             | Native-only decisions: exact register representations and per-safepoint roots, per-instruction direct/guarded choices, specialization regions, semantic protectors, and compiler-site identities. |
| `diagnostics`            | Profile sites, final compiler remarks, and fact-flow reports. Ephemeral optimizer reports remain outside executable artifacts.                                                                    |

Information is not retained merely because an earlier phase once knew it. A fact must
be consumed into a decision, carried explicitly for a later consumer, or discarded
deliberately. Emitters may validate their inputs, but they may not redo Core analysis
or infer native policy from bytecode. An absent native decision means generic
lowering; it does not invite the emitter to guess.

### Consumer contract

| Consumer                           | Runtime image |               Native plan |                                               Diagnostics |
| ---------------------------------- | ------------: | ------------------------: | --------------------------------------------------------: |
| Bytecode interpreter               |           Yes |                        No |                                                        No |
| Runtime wire (`MALW`) and C loader |           Yes |                        No |                                                        No |
| Native-C renderer                  |           Yes |                       Yes | Only final profile annotations required in generated code |
| Compiler artifact (`MALC`)         |           Yes |                       Yes |                                                        No |
| Profile/report generation          |           Yes | Site identities as needed |                                                       Yes |

`MALW` is therefore safe for runtime compilation and relocatable execution: it cannot
accidentally expose compiler-only proof metadata to the VM. `MALC` is an internal
cache artifact that restores the exact native plan instead of reconstructing it. The
formats have distinct magic/version identities and use hard cutovers; there are no
legacy readers or compatibility shims.

### Operation identity

Bytecode opcode names and ordinals have one TypeScript descriptor source. Generation
produces the C include used by both the VM enum and wire loader, and a freshness test
prevents drift. This registry currently owns operation identity. Operand schemas,
effects, constraints, and GC declarations will extend the same descriptor model as
their consumers are migrated; they must not be duplicated in a second registry.

### VM ownership and initialization

The C runtime consumes `MalRuntimeImage`, not the compiler's `ProgramImage`. `MalVm`
keeps an immutable `runtime_image` view backed by a VM-owned `live_runtime_image` for
runtime splicing. Dynamic loading uses explicit runtime-image load, retain, and splice
APIs.

Initialization is ordered into four owning phases:

1. Engine state establishes allocator, GC, completion, and process-independent VM
   state.
2. Program adoption validates generated data and moves growable image tables into the
   VM-owned live image.
3. Execution state allocates frames, roots, caches, and per-function runtime storage.
4. Language state creates globals, intrinsics, constant atoms, shapes, and CommonJS
   state.

Host attachment and host installs happen only after those phases complete. This keeps
engine state, program data, language initialization, and product-host authority from
becoming one implicit constructor contract.

## Optimization consequences

- Closed-world and primordial DCE operate in Core using closure, authority, root, and
  effect facts. The resulting runtime image physically omits dead functions, host
  installs, constants, and metadata; the native plan contains no hidden runtime
  reachability edges.
- Object-shape work records runtime layout descriptors in `RuntimeImage` and guarded
  native use in `NativePlan`. A shape proves layout, not the value class of a slot, so
  representation specialization remains an independent proof.
- GC-aware calls start from each execution function's exact operation and loop-edge
  safepoints, which `NativeFunctionPlan` relocates to bytecode IPs. The current C
  backend consumes their union for its static shadow frame. A future unboxed or
  specialized call ABI must be added only when it is a concrete, verified caller and
  callee decision consumed by native lowering; there is deliberately no placeholder
  always-boxed ABI field for emitters to ignore or reinterpret.
- Interprocedural effects, representations, and call targets remain Core facts until
  consumed into reachability, specialization, allocation, or an explicit execution
  contract. Both backends therefore execute one optimized decision graph.
- Diagnostics are kept separate from executable state, so richer optimization
  explanations cannot silently change runtime or cache semantics.

## Consequences

This is a breaking internal architecture. Target modules, emitted C symbols, runtime
loader APIs, cache result fields, and internal artifact identities use the new
vocabulary directly. The cost is coordinated migrations when contracts change. The
benefit is one inspectable path from facts to decisions to backend consumption, which
is the foundation required for more aggressive IR optimization without semantic or
GC drift.
