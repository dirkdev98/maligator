# VM

## Context

Our current output doesn't fall apart yet, but it is going to. Real soon. We are doing things too naively and should
think things through a bit more.

Let's iterate on general project goals:

- I want to learn JS more.
- I want to learn more about compiler development.

And our specific goals for our AOT compiler to C:

- Spec compliant. A JS engine is only useful if it adheres to the spec.
- Single binary deployement, while running JavaScript.
  - I know there is single executable application (SEA) support now in Node.js, and Bun has had it. But I want it
    myself :)
- Native function interop

So, what are we actually making?

## Decision

As the base form, we are building an ordinary JavaScript runtime Virtual Machine (VM). It has the usual things like
registers, opcodes and stackframes. And on the compiler side we have the usual stuff like lowering to the opcode
instructions, register allocations, metadata collection and what not. All are coming together in a single executable,
preloaded
with the instructions to execute.

But there are a dozen projects like this, so what is our goal. What can we do with an AOT compiled setup?
To be honest, not sure yet. I haven't looked around too much in this space yet, but we could explore a plethora of
paths:

- Instead of JIT-ting, we could do a subset of those optimizations by emitting more specialized ops.
- We could precalculate object shapes and create native C structs and instructions for them.
- We could generate specialized VMs with only a selection of opcodes for various functions.
- We could experiment with different runtime semantics and APIs for coroutine-like concurrency.

And probably much more.

Getting to the full compiler and VM stage is quite the project already. So that will be our initial path forward. I am
no experienced compiler developer or expert on register-based VMs. I'll make mistakes or create weird implementations.
But that's part of the process.

Note that we are pretty much building a bundler in the process as well. Since we need a fixed entrypoint, and want to
pre-lower everything to our bytecode before creating the executable.

## Consequences

It is a lot of work :) With the experimental parts of this project only at the end of a long journey. So we will need
some persistence and patience. We'll get there!
